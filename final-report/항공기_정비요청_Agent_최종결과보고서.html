1. 프로젝트 배경, 목표 및 비즈니스 가치

1.1 배경

항공사 정비통제실에는 운항 중이나 지상에서 발견한 결함 신고가 계속 들어온다. 신고는 "상승 중 객실에서 퀴퀴한 냄새가 남"처럼 자연어로 들어오고, 어느 정비 부서가 맡을지는 통제 담당자가 경험으로 판단한다.

  • 같은 기체에서 최근 반복된 결함인지 매번 이력을 찾아봐야 한다.
  • 증상이 두 계통에 걸쳐 보이면 부서 판단이 사람마다 다르고, 잘못 배정되면 재배정까지 시간이 든다.
  • 왜 그 부서로 보냈는지 근거가 기록으로 남지 않는다.

1.2 목표와 범위

신고가 들어오면 같은 기체의 수리이력과 유사 결함 사례(SDR)를 근거로 담당 부서를 정하고, 근거와 함께 배정한다. 근거가 부족하거나 판단이 엇갈리면 자동 배정을 멈추고 사람 검토로 넘긴다.

2.2 핵심 처리 흐름

  1. 신고자가 요청을 보내면 Spring이 기체 마스터와 대조한다. 누락·충돌이면 아무것도 저장하지 않고 422(NEEDS_SUPPLEMENT)로 응답한다.
  2. 통과하면 요청을 QUEUED로 저장하고 202를 돌려준다. 커밋 후 실행 ID를 새로 만들고, 검색 범위를 기록한 뒤 위임 토큰과 함께 실행 요청을 큐에 넣는다.
  3. AI 서버가 LLM1로 초기 분류한다. 증상만 보고 계통(ATA)을 먼저 정하고, 그 계통의 같은 기체 이력으로 충분하면 바로 배정 결과를 만든다.
  4. 부족하면 LLM2가 LLM1 판단·수리이력을 받지 않고 원본 신고와 RAG로 독립 조사한다. LLM3에서 두 결과를 합쳐 비교하며, 보완 시 최대 2회 독립 재조사한다. AMM은 판단 근거에서 제외하고 배정 결과의 참고자료로 첨부한다.
  5. AI 서버는 근거 원문을 다시 확인한 뒤 결과 이벤트를 보내고, Spring이 근거 ID와 부서를 검증한 뒤 배정한다.
  6. 정비팀이 수락하면 끝나고, 거절하면 사람 검토로 넘어간다. 통제사는 수동 배정하거나 종결한다.

2.3 Agent 설계: State와 Graph

요청 하나를 처리하는 동안 노드들이 함께 쓰는 상태(GraphState)를 두고, 노드는 상태를 읽어 바뀐 필드만 돌려준다. 출력은 Pydantic 스키마로 검사하고, 형식 오류는 오류 내용을 알려 1회 다시 받는다. NextStep의 사용하지 않는 선택 필드 등 의미가 같은 빈 값은 정규화한다. LLM2는 공유 상태 전체가 아닌 InvestigatorState만 받는다.

Agentic 요소는 네 가지다. LLM2·LLM3가 매 단계 다음 행동(도구 호출·마무리·보류)과 도구를 스스로 고른다. LLM3가 두 판단의 근거·계통·부서와 기종 적용성을 대조한다. 재조사는 LLM1 결론이나 LLM3의 구체적 보완 문장을 LLM2에 노출하지 않도록 분리한다. 판정에는 도구 결과에 실제로 있던 근거만 쓴다. 근거가 맞지 않거나 한도를 넘으면 이유 코드와 함께 스스로 멈추고 사람에게 넘긴다.

2.6 레퍼런스 아키텍처와 다른 점

강의 레퍼런스 아키텍처는 business-mcp가 Spring 내부 API(/internal/**)를 거치도록 정한다. 우리 구현은 business-mcp가 조회 전용 계정(mro_business_reader)으로 DB를 직접 읽고, Spring에는 /internal/** 경로가 없다. 업무 규칙이 MCP로 새지 않도록 다음 장치를 두었다.

  • 조회 전용 계정에 필요한 테이블과 agent_request_context·agent_run_context 뷰만 연다. V9에서 V6의 repair_requests 직접 열 권한을 회수했고 신고자 식별 정보는 공개하지 않는다.
  • 도구 호출은 읽기 전용 트랜잭션에서만 실행하고, 서버 시작 시 쓰기 권한이 있는 계정이면 실행을 거부한다.
  • 모든 호출에 실행별 위임 토큰이 필요하고, 토큰의 요청 ID와 다른 요청은 조회할 수 없다. 상태 변경과 배정은 Spring만 한다.
결정 · 유지. MCP 도구는 모두 조회 전용이라 Spring을 거쳐도 얻는 업무 규칙 보호가 없고, 오히려 Spring에 도구별 내부 API와 응답 변환이 생긴다. 대신 전용 뷰 권한(V9), 읽기 전용 트랜잭션, 실행별 위임 토큰과 요청 ID 대조로 같은 경계를 지켰고, 실제 실행에서 토큰 없는 호출 401·다른 요청 조회 FORBIDDEN을 확인했다(4.4).

서버와 검색 방식

business-mcp(8101)와 rag-mcp(8102)는 FastMCP의 streamable HTTP를 사용한다. 공통 인증·응답 형식·읽기 전용 트랜잭션·health 경로를 제공한다. business는 mro_business_reader로 업무 뷰와 이력·부서를, rag는 mro_reader로 RAG 테이블을 조회한다. 공개 도구는 9개이며 모든 도구가 읽기 전용이다.

R02는 단어·벡터 후보를 각각 최대 50건으로 고정한 뒤 합친 순위로 페이지를 나눈다. 페이지마다 후보 집합을 키우던 중복 문제를 막는다. R02·R04 임베딩은 OpenAI text-embedding-3-large 1024차원이다. R02는 질의 인코더 미설정, 릴리스의 SDR 벡터 미준비 또는 임베딩 API 실패 시 경고와 함께 단어 검색으로 대체한다. 고정된 단어검색 색인 자체가 없거나 비정상이면 오류를 반환한다. 한국어 벡터 질의가 가능하지만 단어 검색은 영어 중심이다.

위임 인증과 검색 범위

  1. Spring이 run_id와 rag_request_contexts를 만들고 데이터 release/index, 모델 범위, 만료 시각을 고정한다. request_version과 context_version은 서로 다른 버전이다.
  2. 서버별 위임 토큰(HS256, aud mro-business·mro-rag, 10분)을 RabbitMQ의 x-mro-business-token·x-mro-rag-token 헤더로 전달한다. 토큰은 모델·체크포인트에 저장하지 않는다.
  3. 모든 MCP는 위임 토큰과 요청 ID를 검증한다. B01은 실행 뷰의 활성·만료·context_version을, rag-mcp는 실행 컨텍스트와 고정 릴리스·검색 색인을 추가 검증한다. B02·B03은 입력 context_version을 토큰 값과 대조한다. B01은 agent_request_context·agent_run_context 뷰를 사용하며 V9에서 repair_requests 직접 열 권한을 회수했다.
  4. 현재 시연은 운항사 NULL의 모델 기반 범위다. context_version=2, 정책 airbus-model-scope-v1이며 mapping_revision=backend-v1-model-only와 구분한다. 국내 항공사를 원본 SDR 운항사로 임의 변환하지 않는다.

R02의 기본 MODEL_GENERATION은 같은 기본 모델과 ceo/neo 세대 안에서 검색한다. 초기 검색이 부족하면 이유를 남겨 FAMILY로 넓힐 수 있다. EXACT는 정확한 세부 모델이며, 미확인 모델·이전 NULL 범위는 EXACT만 허용한다. Backend가 허용한 모델 목록은 단어·벡터 검색과 R05에 함께 적용된다. 검색 범위 확장이 정비 구성의 동일성을 뜻하지 않으므로 LLM3가 구성 차이를 검토한다.

5.4 재집계와 시연

평가 수치는 DB·API 호출 없이 공개 번들에서 재집계할 수 있다. LLM·backend·deliverables 저장소를 같은 상위 폴더에 두고 LLM 루트에서 실행한다.

python3 scripts/evaluation/summarize_full_eval.py \
  --bundle ../deliverables/evaluations/2026-10-23-isolated-200 \
  --dataset ../backend/data/eval/service/scenarios.jsonl --check

실구동은 integration의 고정 서비스 커밋과 실행 문서를 따른다. Backend가 DB·큐·스키마·시드·RAG 복원을 준비하고, AI_MODE=rabbit으로 AI와 두 MCP를 연결한다. API 키·위임 토큰 비밀값·DB 비밀번호는 저장소에 넣지 않는다.

  1. 신고자 접수 → LLM1 이력 비교 → 직접 배정 또는 독립 조사·검토 진행을 확인한다.
  2. 정비팀·관리자 화면에서 판단 근거와 별도의 참고 AMM을 확인한다.
  3. 정비팀 거절 → 사람 검토 → 관리자 수동 배정·종결을 확인한다.
  4. 관리자 인원 현황에서 총원·현재 근무·배정 가능 인원을 확인한다. 해당 수치는 아직 자동 배정에 사용하지 않는다.

위 순서는 현재 기능을 확인할 시연 절차이며 이번 문서 개정에서 실제로 재실행한 결과는 아니다. 과거 S10·S23 시연 기록은 raw/에 남겨 두었다.
